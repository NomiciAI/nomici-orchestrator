# v0.1 Living Implementation Plan

## Purpose

This is the working implementation plan for Nomici Orchestrator v0.1 during private bootstrap.

It is intentionally more concrete than the RFCs and more operational than `docs/development-plan.md`. It should change as implementation teaches us what the architecture actually needs.

The goal is not to predict every function. The goal is to keep implementation honest:

- each implementation gate has a runnable exit check
- implemented behavior is separated from intended behavior
- scope can be cut without losing the proof slice
- security and redaction checks happen continuously
- decisions discovered during implementation are captured in the right document

## Recording Rules

Record decisions, not noise.

Before a gate:

- confirm the gate goal
- list hard deliverables
- list degradable deliverables
- list exit commands
- identify docs that may need updates

During implementation:

- update design docs when behavior or boundaries change
- update `CHANGELOG.md` only for notable user-facing or contributor-facing changes
- keep commit messages specific
- do not turn docs into a running diary
- do not start the next gate while the current gate exit checks are failing unless the plan explicitly changes

After a gate:

- record actual behavior
- record known gaps
- update README status if commands become real or remain aspirational
- add follow-up issues before widening scope

Where to write:

- RFCs: architectural decisions that future maintainers need to understand
- `docs/design/`: data models, contracts, state machines, API behavior, safety boundaries
- `docs/implementation/`: current execution plan, implementation gates, sequencing, implementation checklist
- `CHANGELOG.md`: notable project changes
- `README.md`: accurate project/user status only

## Implementation Gate Template

Each implementation gate should have:

```text
Goal:
Hard deliverables:
Degradable deliverables:
Non-goals:
Implementation order:
Exit commands:
Acceptance criteria:
Docs to update:
Risks:
Cut line:
```

The cut line is the smallest version that still proves the gate.

## Gate 0: Scaffold Verification

Goal:

Prove the repository can build and run the minimal local Gateway.

Hard deliverables:

- Go CLI builds.
- Gateway can run locally.
- `/api/health` responds.
- Web scaffold does not break release builds.
- contributor commands are documented and runnable.

Degradable deliverables:

- polished Console shell
- complete make targets for every future package
- release packaging

Non-goals:

- provider setup
- model invocation
- AgentSpec execution
- runtime reconciliation
- trace storage beyond any existing scaffold

Implementation order:

1. Inspect current Go/Web scaffold.
2. Fix build failures only inside scaffold boundaries.
3. Verify CLI version command.
4. Verify Gateway foreground run.
5. Verify `/api/health`.
6. Update README status to match what is real.

Exit commands:

```bash
make build
make test
./bin/nomici --version
./bin/nomici gateway run
curl http://127.0.0.1:8787/api/health
```

Acceptance criteria:

- Commands above succeed on a clean checkout with documented prerequisites.
- `README.md` clearly says only scaffold behavior is implemented.
- `/api/health` follows the documented health-envelope exception.

Risks:

- Web scaffold may require pnpm/node setup that complicates a single-binary story.
- Make targets may imply more than the scaffold actually supports.

Cut line:

Buildable CLI, runnable Gateway, passing health check.

## Gate 1: Provider Setup and Model Profile

Goal:

Let a user configure an LLM provider without writing raw secrets into `nomici.yaml`, then run one Gateway-mediated model test.

Detailed code plan: [Proof Slice Code Plan](proof-slice-code-plan.md) expands Gate 1 and Gate 2 into concrete packages, interfaces, tests, and wiring steps.

Hard deliverables:

- provider profile store
- OpenAI-compatible provider profile
- Ollama provider profile
- secret reference support through environment variables
- provider test command
- capability profile with `true`, `false`, `unknown`
- trace events for provider test

Degradable deliverables:

- rich provider catalog
- latency/cost benchmarking
- Console provider setup
- provider auto-discovery beyond Ollama health probing

Non-goals:

- complex model router
- fallback routing
- cost accounting beyond basic metadata fields
- cloud-provider-specific SDK integrations

Implementation order:

1. Define provider profile schema.
2. Add storage for provider profiles.
3. Implement OpenAI-compatible profile creation.
4. Implement Ollama profile creation.
5. Add provider test through Gateway API.
6. Emit trace events for model test.
7. Add doctor checks and remediation messages.

Exit commands:

```bash
nomici model setup --provider openai-compatible
nomici model setup --provider ollama
nomici model list
nomici model test <model_id>
nomici model doctor
```

Acceptance criteria:

- Raw API keys are never written to `nomici.yaml`.
- Missing env vars produce actionable errors.
- Ollama unavailable produces a clear remediation.
- Model test can run without packs or AgentGraph execution.

Risks:

- Provider setup UX can balloon into a full onboarding system.
- Provider-specific quirks may leak into core too early.

Cut line:

OpenAI-compatible or Ollama setup plus one traceable Gateway-mediated model test.

## Gate 2: Minimal Invoke Path

Goal:

Prove Gateway can mediate one invocation and write a trace, before implementing a rich graph runtime.

Detailed code plan: [Proof Slice Code Plan](proof-slice-code-plan.md) expands Gate 1 and Gate 2 into concrete packages, interfaces, tests, and wiring steps.

Hard deliverables:

- `/api/runs` or equivalent internal run creation path
- one model-backed invocation
- response envelope for non-health API
- trace event persistence
- redacted request/response logging

Degradable deliverables:

- streaming
- cancellation
- replay UI
- token/cost accounting beyond optional metadata

Non-goals:

- full `gateway_agent` loop
- full AgentGraph compiler
- approval queue
- CLI agent runner

Implementation order:

1. Add minimal run record.
2. Invoke configured model profile through provider abstraction.
3. Store trace events.
4. Return normalized response envelope.
5. Add redaction tests.

Exit commands:

```bash
nomici run model <model_id> "Say hello from Nomici"
nomici trace list
nomici trace show <run_id>
```

Acceptance criteria:

- One invocation produces `run.started`, `model.requested`, `model.completed`, and `run.completed` or failure equivalents.
- Trace export redacts secrets.
- Errors include remediation where possible.

Risks:

- This gate can accidentally grow into `gateway_agent`.

Cut line:

One model profile can be invoked through Gateway and traced.

## Gate 3: AgentSpec and Minimal AgentGraph

Goal:

Compile a small AgentSpec into an internal graph snapshot that can drive implemented invocation paths.

Hard deliverables:

- AgentSpec schema validation for implemented fields
- `gateway_agent`, `external_agent`, `model_agent`, and `tool_agent` recognition
- source mapping for validation errors
- internal graph snapshot persistence
- unsupported edge error behavior

Degradable deliverables:

- full canvas layout metadata
- every future edge mode
- migration tooling
- editor autocomplete

Non-goals:

- public IR standard
- full graph optimizer
- durable workflow execution

Implementation order:

1. Define minimal implemented AgentSpec subset.
2. Add JSON Schema validation.
3. Compile source to internal graph snapshot.
4. Add source mapping for errors.
5. Execute only supported node/edge types.
6. Fail unsupported execution modes clearly.

Exit commands:

```bash
nomici spec validate nomici.yaml
nomici graph validate
nomici graph export --format json
nomici run <entrypoint> "Run a minimal graph"
```

Acceptance criteria:

- RFC examples using `gateway_agent` validate where implemented.
- `native_agent` is rejected as non-v0.1 public kind.
- Unsupported edge execution tells the user what is missing.

Risks:

- IR fields may be overbuilt before adapters prove them.

Cut line:

Single-entry graph can validate, snapshot, and invoke one implemented node path.

## Gate 4: Generic CLI Agent Runner

Goal:

Treat command-driven local agents as first-class external runtimes through a generic process contract.

Hard deliverables:

- `cli_agent` runtime kind
- command template rendering
- explicit workspace boundary
- env allowlist/secret refs
- stdout/stderr artifact capture
- exit-code normalization
- timeout/cancel behavior
- workspace lock for mutable runs
- pre/post diff capture for Git workspaces

Degradable deliverables:

- streaming output normalization
- profile auto-detection for every CLI agent
- resume/session support
- editor-native sidecars

Non-goals:

- bespoke Claude Code adapter
- bespoke Codex adapter
- guaranteed visibility into internal tool calls
- bypassing agent-native safety modes

Implementation order:

1. Add CLI runner config model.
2. Implement command-not-found and capability probe path.
3. Implement invoke with argument array or stdin.
4. Add workspace lock.
5. Capture stdout/stderr and diff artifacts.
6. Normalize result into run/task/trace records.
7. Add profiles as presets, not core adapter types.

Exit commands:

```bash
nomici spec validate --config nomici.yaml
nomici graph validate --config nomici.yaml
nomici runtime inspect implementer_cli --config nomici.yaml
nomici agent run implementer "Inspect this repo and summarize it"
nomici trace show <run_id>
```

Acceptance criteria:

- A fake CLI fixture passes contract tests.
- Missing real tools degrade with clear setup guidance.
- Mutable workspace concurrency is prevented or queued.
- Diff artifacts are captured when files change.

Risks:

- Real CLI surfaces change often.
- Some agents may not support reliable non-interactive mode.

Cut line:

Fake CLI fixture plus one locally installed command-driven agent can run through the generic runner.

Implemented bootstrap behavior:

- `cli_agent` runtimes are configured in `nomici.yaml`.
- `nomici runtime inspect <runtime_id>` reads and validates the AgentSpec runtime.
- `nomici agent run <external_agent>` executes one `external_agent` backed by `cli_agent`.
- `runtime add` YAML mutation is deferred until the Runtime Registry edit path exists.

## Gate 5: Shared Context and Handoff Snapshots

Goal:

Make multi-agent handoffs carry useful context without touching agent-native memory.

Hard deliverables:

- `context_items` storage
- `context_snapshots` storage
- adapter request `shared_context` field
- adapter result `context_snapshot` candidate
- validation/redaction before storage
- handoff attachment trace events

Degradable deliverables:

- automatic project-context promotion
- semantic retrieval
- Console context editing
- cross-session learning

Non-goals:

- replacing Hermes/OpenClaw memory
- raw runtime memory import/export
- vector memory
- automatic preference learning

Implementation order:

1. Add context tables and service.
2. Add context selection for a run.
3. Inject briefing into model and CLI adapters.
4. Accept adapter-provided context snapshot candidates.
5. Generate fallback snapshots from output/artifacts.
6. Link snapshots to handoff trace events.

Exit commands:

```bash
nomici context list
nomici run <entrypoint> "Run a handoff"
nomici trace show <run_id>
```

Acceptance criteria:

- Handoff trace shows attached context snapshot.
- Sensitive context is not injected into untrusted runtimes by default.
- Run-scoped context is not reused across runs unless promoted.

Risks:

- Context can become hidden prompt stuffing if selection is not bounded.

Cut line:

Handoff snapshot creation and injection for one supported handoff path.

Implemented bootstrap behavior:

- `context_items` and `context_snapshots` tables exist in SQLite.
- `nomici context list` lists stored context snapshots.
- CLI runner requests carry a `shared_context` briefing field.
- CLI runner results can expose a `context_snapshot` candidate from structured stdout.
- Gateway generates fallback context snapshots from CLI stdout, errors, and artifacts.
- One `handoff` edge between two `cli_agent`-backed `external_agent` nodes executes in a single run.
- Handoff execution emits `context.snapshot.created`, `handoff.created`, `handoff.context_attached`, and `handoff.accepted` trace events.
- General multi-node graph execution remains deferred.

## Gate 6: Policy and Approval v0.1

Goal:

Enable safe partial autonomy by distinguishing low-risk work from actions that need a human gate.

Hard deliverables:

- risk classifier for initial tool/runtime actions
- approval records
- `once` and `run` approval scopes
- approval CLI
- policy trace events
- audit-safe payload summaries

Degradable deliverables:

- session/global scopes
- learned policy exceptions
- rich diff UI
- remote approval notifications

Non-goals:

- policy-as-code language
- RBAC
- multi-user approval

Implementation order:

1. Add policy decision service.
2. Add default low/medium/high/critical tiers.
3. Add approval records.
4. Gate side-effecting tool/runtime requests.
5. Add CLI grant/deny flow.
6. Add audit events.

Exit commands:

```bash
nomici policy check
nomici approvals list
nomici approvals grant <approval_id>
nomici approvals deny <approval_id>
nomici trace show <run_id>
```

Acceptance criteria:

- Low-risk actions are allowed and traced inside declared scopes.
- Medium-risk actions require `once` or `run` approval unless policy explicitly allows them.
- High-risk actions default to `once`.
- Critical-risk actions deny by default.

Risks:

- Too much approval friction makes agents unusable.
- Too little friction makes unattended local work unsafe.

Cut line:

Approval queue with `once` and `run` scopes for one side-effecting action class.

Implemented bootstrap behavior:

- Approval records are stored in SQLite.
- `nomici policy check` prints implemented policy defaults.
- `nomici approvals list`, `nomici approvals grant`, and `nomici approvals deny` are implemented.
- Read-only `cli_agent` execution is allowed and traced.
- Mutable `cli_agent` workspace execution requires approval by default.
- `once` approvals are consumed by the next matching action.
- `run` approvals bind to the next matching run and allow matching actions inside that run.
- Protected system workspaces are denied as critical risk.
- Policy and approval events are written to trace.
- Broader tool/MCP/browser/email policy coverage remains deferred.

## Gate 7: First Useful Pack

Goal:

Ship one bundled pack that proves Nomici is useful immediately after provider setup.

Hard deliverables:

- official bundled pack manifest
- permission review
- install command
- one runnable entrypoint
- traceable run
- clear fallback when optional runtimes are missing

Preferred pack:

```text
developer-team
  product_pm
  architect
  implementer
  reviewer
  test_runner
  human_approval
```

Degradable deliverables:

- all five original demo templates
- polished pack gallery
- remote pack registry
- signed external pack distribution

Non-goals:

- full autonomy
- PR creation
- deploy
- CI repair loops

Implementation order:

1. Define pack manifest fields actually needed by the runner.
2. Bundle `developer-team`.
3. Support optional CLI agent runtime selection.
4. Provide fallback to model-backed nodes or disabled nodes with setup guidance.
5. Run a small end-to-end demo.

Exit commands:

```bash
nomici pack inspect developer-team
nomici pack install developer-team
nomici graph validate
nomici run product_pm "Plan a small implementation task"
nomici trace show <run_id>
```

Acceptance criteria:

- A new user with one configured provider can run the pack.
- Optional Claude Code/Codex/opencode/Aider profiles improve the pack but are not required.
- Permissions are visible before install.
- README quickstart matches actual behavior.

Risks:

- A too-ambitious first pack can hide core bugs.

Cut line:

One official bundled pack, one runnable entrypoint, one inspectable trace.

Implemented bootstrap behavior:

- `developer-team` is available as a bundled official pack.
- `nomici pack list`, `nomici pack inspect developer-team`, and `nomici pack install developer-team` are implemented.
- Pack install uses an existing model provider profile and writes a clean `nomici.yaml`.
- The installed pack includes a runnable `product_pm` entrypoint and `architect` subagent.
- Pack install records the pack under `extensions.packs` in AgentSpec.
- Optional CLI implementer/reviewer/test-runner roles remain pack metadata and are not installed by default.
- Remote pack registry, signed distribution, pack removal, and local pack authoring are deferred.

## Gate 8: Console MVP

Goal:

Give users a local visual surface over implemented Gateway state.

Hard deliverables:

- Dashboard shell
- model/provider list
- pack list/install status
- graph read-only view
- runtime status
- run/trace timeline
- approval list

Degradable deliverables:

- full visual canvas editing
- Console-first provider setup
- advanced trace replay
- artifact preview for all formats

Non-goals:

- cloud dashboard
- multi-user auth
- remote team mode

Implementation order:

1. Embed built Console assets in Gateway.
2. Add API client with token flow.
3. Render Dashboard from Gateway APIs.
4. Render graph read-only from compiled graph snapshot.
5. Render traces and approvals.

Exit commands:

```bash
nomici gateway run
open http://127.0.0.1:8787
```

Acceptance criteria:

- Console does not receive raw secrets.
- Console uses Gateway APIs only.
- Console clearly marks non-implemented actions as unavailable.

Risks:

- UI work can pull scope toward a product surface before the control plane is proven.

Cut line:

Read-only Console for provider, pack, graph, runtime, trace, and approval state.

Implemented bootstrap behavior:

- Gateway exposes read-only Console APIs for overview, models, packs, latest graph, runtimes, runs, and approvals.
- Gateway protects non-health Console/API endpoints with bearer-token auth. The token is loaded from `NOMICI_GATEWAY_TOKEN` or created in `.nomici/gateway.token`; CLI commands forward it automatically, and Console prompts for it.
- Pack installations are recorded in SQLite so Console can show installed status without reading `nomici.yaml`.
- Console renders model profiles, bundled pack status, latest graph snapshot, configured runtimes, recent runs, latest trace timeline, pending approvals, and unavailable Gate 8 actions.
- Console uses Gateway APIs only and does not receive raw secret values.
- Console editing, provider setup, runtime lifecycle controls, live event streaming, and trace replay remain deferred.

## Gate 9: Pre-Public Hardening

Goal:

Prepare the private repository for quiet public release without leaking private product details or overstating implementation status.

Hard deliverables:

- open-source checklist complete
- strict branch protection restoration captured as a quiet-public precondition
- Gateway token auth enabled for non-health API routes
- README implementation status accurate
- secret scan
- GitHub Actions baseline
- install script reviewed
- security docs reviewed
- license and governance files checked

Degradable deliverables:

- Homebrew/npm/pipx distribution
- signed binaries
- SBOM automation
- full release drafter

Non-goals:

- public marketing launch
- marketplace
- team/server features

Exit commands:

```bash
git rev-parse --show-toplevel
git status --short
git remote -v
git ls-files
make test
make lint
```

Acceptance criteria:

- Repository root is `nomici-orchestrator`.
- Remote points to `NomiciAI/nomici-orchestrator`.
- `README.md` and docs do not expose private product internals.
- `CODEOWNERS` references real org/team.
- Open-source publication checklist is complete.
- Bootstrap branch protection state matches the checklist until the owner explicitly approves quiet public.

Risks:

- Accidental leakage from sibling product repositories.
- Quickstart claims functionality not yet implemented.

Cut line:

Quiet public-ready repo with accurate docs and safe GitHub settings.

## Continuous Checks

Run before every implementation commit where relevant:

```bash
git diff --check
make test
make lint
grep -R --exclude-dir=dist --exclude-dir=node_modules -n -E '(sk-[A-Za-z0-9]{10,}|api_key:\s|password:\s|secret:\s|BEGIN (RSA|OPENSSH|PRIVATE) KEY|Authorization: Bearer [A-Za-z0-9]{10,})' README.md CHANGELOG.md docs .github SECURITY.md internal cmd apps packages || true
```

For docs-only changes:

```bash
git diff --check
rg -n '(sk-[A-Za-z0-9]{10,}|api_key:\s|password:\s|secret:\s|BEGIN (RSA|OPENSSH|PRIVATE) KEY|Authorization: Bearer [A-Za-z0-9]{10,})' README.md CHANGELOG.md docs || true
```

For Gateway/API changes:

```bash
make test
./bin/nomici gateway run
curl http://127.0.0.1:8787/api/health
```

For Console changes:

```bash
pnpm --dir apps/web lint
pnpm --dir apps/web build
```

Only keep checks that exist in the current scaffold. If a listed command does not exist yet, either implement the command in the relevant gate or update this plan to mark it deferred.
